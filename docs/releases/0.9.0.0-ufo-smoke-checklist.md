# v0.9.0.0-UFO archived on-device smoke checklist

Archived with the v0.9.0.0-UFO release (issue #45). Per the series'
hardware-acceptance policy, review-complete and host-tested code shipped
without on-device gates; this checklist aggregates every hardware acceptance
item the release carries, each linking its authoritative tracking issue
(steps, expected observations, and rollback live there — this page orders and
summarizes them for a release qualification pass). Executing an item and
recording the result closes the corresponding issue.

Suggested order: boot/update integrity first (a failure there invalidates
everything after it), then the settings substrate, then the feature paths.

## 1. Boot, update and integrity

| # | Item | Tracking issue | Summary |
|---|---|---|---|
| 1.1 | SD-card update accepts an emitter-produced image | [#60](https://github.com/ChrisUFO/M1/issues/60) | Install a `_wCRC.bin` built by the Python CRC emitter over the SD update path; device boots it with the CRC gate passing; repeat with the `srec_cat`-produced image of the same revision and confirm identical behavior; record image SHA-256 + device revision. |
| 1.2 | CDC RX diagnostics under stress transfer | [#63](https://github.com/ChrisUFO/M1/issues/63) | During a stress transfer, the `status` counters (refused-at-arrival, lost, buffered-now) go non-zero only under genuine pressure and never for a healthy link (#44 gate). |
| 1.3 | HW RNG bring-up, USB attached + unplugged | [#83](https://github.com/ChrisUFO/M1/issues/83) | No `HW RNG init failed -- crypto refuses` boot line in either power regime; the post-init generate probe is consumed; a failing RNG refuses crypto but never blocks boot. |

## Recording results

Record each item's evidence (device revision, build manifest SHA-256 from the
release verification record, pass/fail, notes) on the tracking issue linked
above. A failed item does not invalidate the release artifacts; it opens a
fix against the affected subsystem with the rollback noted in the issue.
