# CRC emitter parity golden expectations (issue #40).
#
# The authoritative values in this table were produced by the canonical
# srecord pipeline -- NOT by the Python emulator:
#
#   srec_cat <in>.bin -binary -crop 0x0 0x000FFC14 \
#       -STM32_Little_Endian 0x000FFC14 -o <out>_wCRC.bin -binary
#
# (SRecord from Debian/Ubuntu; the invocation is byte-for-byte the one
# CMakeLists.txt uses when srec_cat is on PATH.)
#
# Inputs are generated deterministically by tools/crc_test_vectors.py:
#   zeros       0x00 fill
#   ff          0xFF fill
#   ramp        byte i = i mod 256
#   xorshift32  xorshift32 seed 0x12345678, serialized as 32-bit LE words
# Every input is exactly 1047572 bytes (0xFFC14). Every expected output is
# exactly 1047576 bytes (0xFFC18): the cropped image followed by the 32-bit
# CRC-32/MPEG-2 result, little-endian, at offset 0x000FFC14.
#
# Columns (whitespace separated):
#   name  input_sha256  output_sha256  crc_le_bytes
# crc_le_bytes is the 4-byte CRC field in on-disk (= little-endian) byte order,
# so "5688a4fc" is the word 0xFCA48856.
#
# scripts/verify_crc_parity.sh regenerates the inputs, checks these input
# digests (generator drift), re-runs the emitter, and compares its output
# digests + CRC field against this file. When srec_cat is installed it also
# re-runs the authoritative pipeline and byte-compares the two emitters.
#
# Regeneration is gated: the ONLY sanctioned way to rewrite this table is
#
#   sh scripts/verify_crc_parity.sh --update-golden
#
# on a host where srec_cat is on PATH. The script refuses without srec_cat and
# verifies the emulator agrees byte-for-byte before writing, because a table
# re-baselined from the Python emulator would grade the emulator against itself
# and make the one host-independent parity check circular.
